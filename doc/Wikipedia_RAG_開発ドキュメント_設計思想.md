# Wikipedia RAG 開発ドキュメント（設計思想・開発履歴）

# 1. この文書について

本書は、検索アルゴリズムの「なぜその設計になったか」を残すための開発ドキュメントである。
ソースコードの説明ではなく、設計判断・試行錯誤・今後改善する際の判断基準を記録することを目的とする。

------------------------------------------------------------------------

# 2. 開発当初の構成

    質問
     ↓
    Embedding
     ↓
    FAISS
     ↓
    上位チャンク
     ↓
    LLM

設計自体は一般的なRAGであり、Wikipedia全体を一度に検索していた。

Embeddingには

-   タイトル
-   セクション
-   本文

を含めており、float16ベクトルをSQLiteへ保持して再ランキングも行っていた。

そのため、検索精度が悪い場合はEmbeddingやFAISSに原因があると当初は考えていた。

------------------------------------------------------------------------

# 3. 調査で分かったこと

ソースコードを調査した結果、

-   prefixは適切
-   cosine検索も適切
-   float16 rerankも実装済み
-   タイトルEmbeddingも実装済み

であり、基礎部分には大きな問題は見つからなかった。

つまり問題は検索アルゴリズムそのものではなく、「質問の扱い方」にある可能性が高くなった。

------------------------------------------------------------------------

# 4. 問題の本質

例

    ロサンゼルス・ドジャースの大谷翔平について教えて

旧方式では、この全文をEmbedding検索していた。

しかし各チャンクには

    タイトル: ロサンゼルス・ドジャース

が埋め込まれているため、記事内チャンク同士の差が小さくなる。

結果として

-   球団史
-   本拠地
-   歴史

などが上位になり、大谷翔平のチャンクが埋もれることがあった。

これは

「記事は見つかるが、記事内の目的箇所が見つからない」

という現象だった。

------------------------------------------------------------------------

# 5. 発想の転換

Wikipedia検索には二種類ある。

1.  どの記事か探す
2.  記事内のどこか探す

旧方式では両方を一回のEmbedding検索へ押し込んでいた。

これを二段階へ分離した。

    質問
     ↓
    記事検索
     ↓
    記事決定
     ↓
    記事内検索
     ↓
    LLM

これが今回最大の変更点である。

------------------------------------------------------------------------

# 6. autoモード

新しいautoは

・記事タイトルが確定 →記事内再検索

・確定しない →従来検索

というフォールバック構造である。

安全性を保ったまま精度だけを改善することを目的とした。

------------------------------------------------------------------------

# 7. 記事内クエリ

例

質問

    ファイナルファンタジーXIVの漆黒のヴィランズについて教えて

↓

記事

    ファイナルファンタジーXIV

↓

記事内クエリ

    漆黒のヴィランズ

このクエリで記事全チャンクを再順位付けする。

------------------------------------------------------------------------

# 8. 実験結果

代表例

・ロサンゼルス・ドジャースの大谷翔平
・ファイナルファンタジーXIVの漆黒のヴィランズ

どちらも旧方式では目的チャンクが取得できない場合があったが、新方式では正しく引用できた。

この結果から、改善の主要因はEmbedding変更ではなく検索手順であると判断した。

------------------------------------------------------------------------

# 9. 副次的効果

検索精度だけでなく、

・LLMへ渡す文字数減少 ・入力トークン減少 ・生成速度向上

も確認された。

検索エンジン側で記事内を十分絞れるため、LLMは回答生成へ集中できる。

------------------------------------------------------------------------

# 10. 今後改善する場合の原則

改善対象は

・記事内検索 ・クエリ生成 ・記事内ランキング ・コンテキスト生成

を優先する。

EmbeddingやFAISSは最後に検討する。

------------------------------------------------------------------------

# 11. 優先順位

1.  記事内FTS
2.  前後チャンク展開
3.  lexical score
4.  コンテキスト最適化
5.  RRF

------------------------------------------------------------------------

# 12. 設計思想

検索エンジンは

「どの記事」 「記事内のどこ」

まで決める。

LLMは

「その情報をどう説明するか」

だけを担当する。

この責務分離を維持することが、このRAG全体の基本方針である。
